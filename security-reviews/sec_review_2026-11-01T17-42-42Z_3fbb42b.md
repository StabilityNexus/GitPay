## Findings

### Finding 1: `MEMBER` and `COLLABORATOR` are trusted to spend without write access — `src/adapters/github/trigger.ts:140`

- Severity: High
- Confidence: 0.85
- Category: access_control
- Description: The maintainer gate (`MAINTAINER_APPROVED`) passes when the comment's
  `author_association` is in `allowed_associations`, which defaults to
  `OWNER,MEMBER,COLLABORATOR` (`trigger.ts:140`, `action.yml` `allowed_associations` default).
  The code describes that set as "people who can be trusted to spend the project's money", but
  GitHub's `author_association` does not encode repository permission. `MEMBER` means "a member
  of the organization that owns the repository" — every org member, including members with no
  access to this repository beyond read. `COLLABORATOR` includes outside collaborators granted
  only `read` or `triage`. Nothing else in the `/send` path checks the commenter's permission,
  so the gate is wider than the write-access boundary the rest of the design assumes ("editing
  a workflow already requires write access").
- Exploit Scenario: GitPay is installed in a repository owned by an organization with many
  members (a typical open-source org, where contributors are often added as members for
  project-board or Discord-role reasons). A member with no write access to this repository
  comments `/send 0xTheirAddress 5` on any open pull request. The association is `MEMBER`, the
  gate passes, and the delegate pays 5 USDC to them from the Safe. Repeating it with `round:1`,
  `round:2`, … or on other PRs pays again each time, up to `max_per_payout` per payout and the
  Safe's period allowance (or the remaining ERC-20 approval) overall.
- Recommendation: Gate `/send` on the commenter's actual repository permission, not on
  `author_association` alone. In the GitHub adapter, call
  `GET /repos/{owner}/{repo}/collaborators/{username}/permission` with the workflow token and
  require `write`, `maintain` or `admin`. Keep `allowed_associations` as an additional filter,
  so the change can only narrow who may spend. Give `github_token` a default of
  `${{ github.token }}` so the default dry-run template keeps working without new inputs.

### Finding 2: Receipt comments are believed from non-writers and from any bot — `src/adapters/github/receipts.ts:132`

- Severity: Low
- Confidence: 0.75
- Category: access_control
- Description: `isTrustedReceiptAuthor` believes a receipt marker written by any account of
  type `Bot` (`receipts.ts:135`) or whose association is `OWNER`, `MEMBER` or `COLLABORATOR`
  (`receipts.ts:132`). The comment above it states the intent: "a contributor should not be
  able to block someone else's payout with a comment". For the reason given in Finding 1, an org
  member or a read-only collaborator passes this check without being able to spend. Any GitHub
  App installed on the repository also passes, including review bots that quote PR text back
  into their own comments.
- Exploit Scenario: The idempotency key is printed in every run log and is predictable from the
  repository, PR number, recipient and asset. A read-only org member posts
  `<!-- xops-receipt:v1 key=<key> status=settled tx=0x00… -->` on the PR before a maintainer
  sends `/send`. The run reports `already-paid` against a transaction that does not exist, and
  the contributor is not paid until a maintainer notices and bumps `round`. Nothing is stolen.
  The failure is a withheld payout, which the design deliberately prefers over a double one.
- Recommendation: Believe a receipt only from the identity that writes receipts (the token's
  own bot account), or apply the same repository-permission check as Finding 1 to the receipt's
  author. At minimum, drop `MEMBER` and `COLLABORATOR` from `TRUSTED_ASSOCIATIONS` unless they
  are confirmed to have write access.

### Finding 3: A malformed delegate key is echoed into the error message and the run log — `src/drivers/evm/rlp.ts:21`

- Severity: Low
- Confidence: 0.85
- Category: data_exposure
- Description: `addressFromPrivateKey` and `signTransaction` (`src/drivers/evm/tx.ts:59`,
  `tx.ts:84`) pass the delegate private key to `hexToBytes`, which throws
  ``odd-length hex: "${hex}"`` (`rlp.ts:21`) or ``not hex: "${hex}"`` (`rlp.ts:25`) with the
  whole input embedded. `main.ts` prints the message of any uncaught error with
  `console.error`. Separately, `Number.parseInt` accepts a valid hex prefix, so a character such
  as `0g` parses as `0` instead of being refused. A mistyped key is silently turned into a
  different key rather than rejected.
- Exploit Scenario: An adopter stores the delegate key with a stray character or an odd length.
  Common causes are a missing digit when copying it, or a key fetched from an external secret
  manager by an earlier step that did not call `::add-mask::`. The first `mode: self` run fails
  constructing the driver, and the full key is printed into the Actions log. On a public
  repository anyone can read that log. GitHub's automatic masking protects only values stored as
  registered secrets, so this depends entirely on how the key reached the job.
- Recommendation: Validate the key with a strict `^(0x)?[0-9a-fA-F]{64}$` before it reaches
  `hexToBytes`, and throw a message that names the problem without the value. Make `hexToBytes`
  reject any non-hex character and stop quoting its input in errors.

## Notes

### Note 1: A leaked delegate key can spend the full allowance every period — `src/drivers/safe-allowance/driver.ts:47`

- Category: accepted-risk
- Observation: CI holds the delegate key. A leaked key can call `executeAllowanceTransfer` to
  any address, up to the period allowance, every period until a Safe owner removes the
  delegate. Under `approve` it can spend whatever remains of the ERC-20 approval, once.
- Rationale: This is the stated custody model. `AGENTS.md` ("The delegate key, stated
  honestly") and `DECISION-LOG.md` §6a document it, and `SECURITY.md` lists it as out of scope.
  The drivers declare `needsSecret: true`, and the registry runs them at Tier 1 on purpose.

### Note 2: The receipt ledger is check-then-act and relies on the adopter serializing runs — `src/core/ledger.ts:105`

- Category: design-tradeoff
- Observation: `lookup` → `record` → `broadcast` is not atomic. Two concurrent runs for the
  same key can both miss the receipt and both pay.
- Rationale: The project has no server to hold a lock, by design ("an artifact, not a
  service"). `AGENTS.md`, `LEDGER_RACE_WARNING` and every adopter template require a job-level
  `concurrency` group with `cancel-in-progress: false`.

### Note 3: No GitPay-level cap unless `max_per_payout` is set — `src/main.ts:159`

- Category: design-tradeoff
- Observation: With `max_per_payout` unset, `AMOUNT_WITHIN_CAP` is skipped and a single `/send`
  can request up to the full on-chain allowance.
- Rationale: Documented in `action.yml` and in `AGENTS.md` ("The period cap is the real bound").
  The run log warns on every real settlement without one, and the templates set
  `max_per_payout`.

## Limitations

**Standing limitations**

- This review does not replace a full manual audit or a penetration test.
- This is static analysis of source text. Nothing was executed, fuzzed, or traced at runtime,
  so timing-dependent, load-dependent, or infrastructure-dependent issues cannot be confirmed
  here.
- Confidence scores are the reviewing model's own self-assessment, not a calibrated
  statistical probability.
- Absence of a reported finding does not mean the code is secure. Safety guardrails built into
  some models can cause a real vulnerability to be softened, generalized, or left out rather
  than reported in exploit-level detail, and training-data bias can make some vulnerability
  classes easier for a model to recognize than others. Treat this report as a floor on what a
  full audit would find, not a ceiling.
- Findings reflect the reviewing model's training data cutoff. A vulnerability tied to a very
  recently disclosed CVE or library advisory may not be recognized as such.

**Review-specific limitations**

- The on-chain contracts this code calls were not reviewed: the Safe AllowanceModule
  (`0xCFbFaC74C26F8647cBDb8c5caf80BB5b32E43134`) and whatever ERC-20 an adopter configures. The
  review relies on the project's own account of their behaviour.
- The runtime dependencies `@noble/curves` and `@noble/hashes` and the bundled `dist/index.js`
  were not reviewed. CI's rebuild-and-diff check (I12) is what ties `dist/` to `src/`.
- The `frontend/` site was reviewed by searching for sinks, not file by file. It is static,
  ships no server code, and is out of scope in `SECURITY.md`.
- Behaviour of GitHub's `author_association` and of the collaborator-permission endpoint
  (Findings 1 and 2) comes from GitHub's documentation and was not re-verified against a live
  organization for this review.
- Third-party actions used by the repository's own workflows (`peakoss/anti-slop`,
  `eps1lon/actions-label-merge-conflict`, `danger`) were checked only for how they are invoked.
  They are SHA-pinned and receive no PR checkout.
